# 架构与安全边界

## 为什么不做通用面板

宝塔那类面板允许在网页上执行任意 shell、浏览任意文件、安装任意软件。
这种通用性带来一个后果：**面板一旦被攻破，等于交出整台服务器的 root**。
历史上宝塔多次因此出现严重漏洞。

Nova 的场景不需要通用性——只有一个应用、一套环境、一台机器。
所以这里的设计是：

> 面板是一个**固定动作的白名单工具**，不是远程终端。

具体表现：

- 界面上每个按钮对应一个写死的脚本，参数经过白名单校验后才拼接
- 不存在「输入命令并执行」的入口
- 不存在「浏览任意目录」的入口
- 文件上传只接受 zip，且校验内部结构与文件类型白名单

## 三层结构

```
┌─────────────────────────────────────────┐
│  第三层：Web 面板（Go，独立端口）        │
│  只做界面与编排，不直接操作 shell        │
└────────────────┬────────────────────────┘
                 │ 调用
┌────────────────▼────────────────────────┐
│  第二层：nova CLI / scripts/*.sh        │
│  真正的动作实现，SSH 里也能直接用        │
└────────────────┬────────────────────────┘
                 │ 操作
┌────────────────▼────────────────────────┐
│  第一层：install.sh                     │
│  裸机 → 可运行环境，只跑一次             │
└─────────────────────────────────────────┘
```

**为什么面板必须独立于 nova-api**：

如果面板跑在业务 JVM 里，nova-api 崩溃时面板一起挂，你就没法通过面板重启它。
所以面板是独立进程、独立端口、独立 systemd unit。

**为什么先做 CLI 再做界面**：

面板的每个按钮最终都要调脚本。先把脚本打磨稳定（错误处理、幂等、日志），
面板就是薄薄一层。反过来先做界面，业务逻辑会散落在 UI 代码里，以后改不动。

## 安全红线

以下每一条都必须做到，缺一条就退回「只用 CLI、不开 Web 面板」。

| 项 | 要求 |
| --- | --- |
| 网络暴露 | 面板端口不对外开放，绑内网 IP 或防火墙白名单 |
| 传输 | 强制 HTTPS，不提供 HTTP 入口 |
| 认证 | 独立账号体系，不复用 Nova 用户表，密码 bcrypt（cost ≥ 12） |
| 会话 | HttpOnly + Secure + SameSite=Strict Cookie，空闲超时 30 分钟 |
| 权限 | 面板进程用受限用户运行，需要提权的少数动作走 sudo 白名单 |
| 审计 | 所有写操作记录操作人、时间、参数、结果 |
| 上传 | 只接受 zip，校验结构、大小上限、解压后路径不得越界（防 zip slip） |
| 命令注入 | 所有外部命令用参数数组形式调用，禁止字符串拼接后交给 shell |

## 部署流程

```
上传 zip
   ↓
校验（结构 / 大小 / 版本清单 / 路径越界）
   ↓
解压到 releases/<时间戳>/
   ↓
备份数据库（改表结构的版本必须先备份）
   ↓
停止 nova-api
   ↓
切换软链 current → releases/<时间戳>
   ↓
启动 nova-api
   ↓
健康检查（/api/health 连续 N 次成功）
   ↓
  ├─ 通过 → 清理旧版本（保留最近 5 个）
   └─ 失败 → 自动回滚到上一个版本 + 告警
```

**关键点**：

1. **先备份再动**。像 V14 那种加列的迁移，跑挂了没备份就只能重建。
2. **软链切换**。`current` 指向哪个目录就是哪个版本，回滚只需改软链 + 重启。
3. **健康检查失败必须自动回滚**。只提示「部署失败」而不回滚，等于把站点留在半死状态。
4. **保留历史版本**。没有回滚能力的部署系统是不合格的。

## 备份策略

「每天 mysqldump 到同一个盘」不是备份。要求：

| 维度 | 做法 |
| --- | --- |
| 内容 | MySQL 全量（`--single-transaction --routines --triggers`）+ uploads 目录 |
| 异地 | 至少一份同步到对象存储（OSS/COS/S3）或另一台机器 |
| 保留 | 日备 7 份、周备 4 份、月备 3 份 |
| 验证 | 面板提供「试恢复到临时库」，确认备份真的可用 |
| 加密 | 含用户数据，上传对象存储前加密 |
| 监控 | 备份失败要告警，不能静默 |

**为什么要试恢复**：备份文件可能是 0 字节、可能权限不对、可能 mysqldump 中途失败
但退出码是 0。只有真的恢复一次，才知道备份有效。

## 磁盘监控

Nova 的图片上传不压缩、不生成缩略图，磁盘增长比一般项目快。
按每人每月 20 张 × 2MB 算，100 个活跃用户约 4GB/月。

磁盘写满是最常见的线上事故，且症状很诡异（MySQL 拒绝写入、上传静默失败）。
面板必须：

- 显示磁盘使用率
- 超过 80% 告警
- 超过 90% 在首页顶部挂红条

## 技术选型

**Go 单二进制**，理由：

- 编译成一个文件扔上去就能跑，无运行时依赖（不像 Java 要带 JRE）
- 交叉编译方便（`GOOS=linux GOARCH=amd64`）
- 标准库足够（`net/http`、`os/exec`、`html/template`），不需要框架
- 静态资源用 `embed` 打进二进制，部署只有一个文件

**不用 Java**：面板如果也用 JVM，一台 2C4G 机器上跑两个 JVM 太浪费，
而且面板要能在业务 JVM 出问题时独立存活。

## 与 Nova 业务代码的关系

**完全独立**：

- 不同的仓库（业务在 `NOVA`，面板在 `NOVA-MB`）
- 不同的发布节奏
- 面板**不 import** 任何业务代码，只通过文件系统与 systemd 操作
- 业务代码升级不需要动面板；面板升级不影响业务

唯一的耦合点是**约定**：部署包结构、`/etc/nova/env` 的环境变量名、
健康检查路径。这些约定写在 `docs/OPERATIONS.md` 里。
